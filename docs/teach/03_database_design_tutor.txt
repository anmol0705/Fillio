ABOUT THE PROJECT
================================================================================

Filio is a work management application for CA (Chartered Accountant) firms in
India. The database must:
  - Store tasks, clients, users, and organisations
  - Keep a permanent, tamper-proof audit trail of every action
  - Support multiple CA firms sharing the same database without seeing each other
  - Enforce permissions at the database level (not just application level)
  - Handle recurring task templates and attendance tracking

Database: PostgreSQL 16, hosted on Supabase (Mumbai region)
ORM: Drizzle ORM (TypeScript) with postgres-js driver
Connection: Via PgBouncer pooler (port 6543) for app, direct (port 5432) for migrations

TOPIC 1: THE FUNDAMENTALS — WHAT IS A RELATIONAL DATABASE?
================================================================================

The spreadsheet analogy:
Think of a database as a collection of spreadsheets (called TABLES) that can
reference each other.

In a single spreadsheet you might have:
  | Task Title    | Assignee Name | Client Name        |
  |---------------|---------------|--------------------|
  | File GSTR-3B  | Rahul Sharma  | Mehta Constructions|
  | TDS Return Q1 | Priya Singh   | Rajesh Textiles    |

The problem with this: if Rahul Sharma changes his name, you must update every
row that mentions him. If "Mehta Constructions" becomes "Mehta Builders", same
problem. Data is repeated everywhere.

The relational solution: SEPARATE TABLES with IDs.

  TASKS table:
  | id   | title         | assignee_id | client_id |
  |------|---------------|-------------|-----------|
  | t001 | File GSTR-3B  | u001        | c001      |

  USERS table:
  | id   | name          |
  |------|---------------|
  | u001 | Rahul Sharma  |

  CLIENTS table:
  | id   | name                |
  |------|---------------------|
  | c001 | Mehta Constructions |

Now if Rahul changes his name, update ONE row in USERS. All tasks still point to
u001 and automatically reflect the new name.

This is called NORMALISATION — eliminating redundancy.

A FOREIGN KEY is a column in one table that refers to the id in another table.
tasks.assignee_id is a foreign key → profiles.id.

TOPIC 2: THE 11 TABLES IN FILIO
================================================================================

Filio has 11 tables. Think of them as 11 spreadsheets that are all connected.

TABLE 1: orgs
  Purpose: Stores each CA firm. One row per firm.
  Columns: id, name, slug, created_at
  Key fact: Every other table has an org_id column pointing here.
            This is how multi-tenancy works — every piece of data knows which firm it belongs to.
  Example row: { id: 'abc123', name: 'Sharma & Associates', slug: 'sharma-associates' }

TABLE 2: roles
  Purpose: The job titles / hierarchy inside a firm.
           Founding Partner → Manager → Article Assistant → Intern
  Key columns: id, org_id, name, color, parent_role_id, sort_order
  Key fact: parent_role_id points to ANOTHER ROW IN THE SAME TABLE.
            This is called a SELF-REFERENCING TABLE. It allows an unlimited-depth hierarchy.
  Example: Founding Partner has parent_role_id = NULL (top of the tree)
           Manager has parent_role_id = id of Founding Partner

TABLE 3: profiles
  Purpose: Every person who uses Filio has a profile. One row per person per firm.
  Key columns: id, org_id, role_id, full_name, email, is_org_admin, is_active
  KEY FACT: profiles.id = auth.users.id (same UUID as the Supabase Auth user)
            This links the auth system to the application data.
  No FK declared in Drizzle: Supabase manages auth.users in a separate schema.
                              Drizzle cannot reference it. The link is by UUID convention.

TABLE 4: clients
  Purpose: The CA firm's client companies.
  Key columns: id, org_id, name, pan, gstin, contact_email, is_active
  PAN = 10-char taxpayer ID. GSTIN = 15-char GST registration number.
  Tasks are linked to clients.

TABLE 5: tasks
  Purpose: The core entity. Every unit of work.
  Key columns: id, org_id, title, task_type, status, priority, client_id,
               assignee_id, creator_id, financial_year, due_at, is_open_pool, is_active
  This is the central table. Most of the app is built around reading and updating it.
  is_open_pool: true = anyone in the org can see and claim this task
                false = only people in task_access can see it

TABLE 6: task_access
  Purpose: THE PERMISSION BACKBONE. Who can see/edit which task.
  Columns: id, task_id, user_id, access_level (owner/editor/viewer)
  UNIQUE constraint: (task_id, user_id) — one access row per person per task
  A user can see a task ONLY if they have a row here (or the task is open pool).
  This table has NO INSERT/UPDATE/DELETE RLS policies — only the admin client
  can write to it. This prevents users from granting themselves access.

TABLE 7: task_messages
  Purpose: The chat thread inside each task.
  Columns: id, task_id, sender_id, content, file_url, file_name, created_at
  content and file_url are both NULLABLE — a message can be text, a file, or both.
  NO UPDATE/DELETE policy — messages are immutable once sent.

TABLE 8: task_audit_log
  Purpose: The permanent, tamper-proof record of every action on every task.
  Columns: id, task_id, actor_id, action, old_value, new_value, created_at
  action is one of: created | status_changed | reassigned | comment_added |
                    file_uploaded | access_granted
  NO INSERT/UPDATE/DELETE RLS policy for ordinary users.
  Admin client inserts ONLY.
  No UPDATE or DELETE policy EXISTS — period. Even Postgres cannot be made to
  update or delete these rows from the application code.

TABLE 9: recurring_templates
  Purpose: Configuration for automatically-generated recurring tasks.
  Key columns: id, org_id, title, task_type, cadence, default_priority,
               default_assignee_role_id, default_client_id, days_before_due, is_active
  cadence: monthly | quarterly | half_yearly | annually
  At cron time, looks up a user with default_assignee_role_id and assigns to them.

TABLE 10: attendance_records
  Purpose: Daily attendance for all staff.
  Columns: id, org_id, user_id, date, status, note
  status: present | absent | half_day | leave
  UNIQUE constraint: (user_id, date) — one record per person per day.
  This enables UPSERT (if you mark attendance twice for the same day, it updates
  the existing record rather than creating a duplicate).

TABLE 11: notifications
  Purpose: In-app notification inbox.
  Columns: id, org_id, user_id, task_id, title, body, is_read
  No INSERT RLS policy — admin client only inserts notifications.
  UPDATE policy allows users to set is_read = true on their own notifications.

TOPIC 3: DATA TYPES AND ENUMS
================================================================================

PostgreSQL ENUM:
An enum is a column that can only hold one of a predefined list of values.
Like a dropdown — you can only pick from the available options.

Filio has 7 enums:

  task_type: 'gst' | 'tds' | 'income_tax' | 'audit' | 'roc_mca' | 'accounting'
             | 'payroll' | 'notice' | 'advisory' | 'other'

  task_status: 'not_started' | 'in_progress' | 'under_review' |
               'changes_requested' | 'approved' | 'filed' | 'completed'

  task_priority: 'urgent' | 'high' | 'medium' | 'low'

  access_level: 'owner' | 'editor' | 'viewer'

  attendance_status: 'present' | 'absent' | 'half_day' | 'leave'

  audit_action: 'created' | 'status_changed' | 'reassigned' | 'comment_added'
                | 'file_uploaded' | 'access_granted'

  recurring_cadence: 'monthly' | 'quarterly' | 'half_yearly' | 'annually'

Why enums instead of just storing the string?
  1. DATABASE ENFORCES VALID VALUES. You cannot store "URGENT" (wrong case)
     or "very_high" (not in list). The database rejects it.
  2. Storage efficiency. Enums are stored as integers internally.
  3. Clarity. Reading the schema tells you exactly what values are valid.

Why the date column in attendance_records is type date (not timestamp):
  A timestamp stores a specific moment in time: "2026-07-18 14:32:05 UTC".
  A date stores a calendar day: "2026-07-18".
  Attendance is about the calendar day, not the exact moment you marked it.
  If you stored a timestamp, "July 18th attendance marked at 2 PM" would be
  different from "July 18th attendance marked at 9 AM" — but they mean the
  same attendance day. date avoids this confusion.

TOPIC 4: RELATIONSHIPS BETWEEN TABLES
================================================================================

There are three types of relationships:

ONE-TO-ONE:
  One profile has one auth user. profiles.id = auth.users.id. 1:1.

ONE-TO-MANY (the most common):
  One org has many tasks. One client has many tasks. One user creates many tasks.
  Example: tasks.assignee_id → profiles.id
  One profile (user) can be the assignee of MANY tasks.

MANY-TO-MANY:
  One task can be accessed by many users. One user can have access to many tasks.
  This is a many-to-many relationship, implemented via task_access (a junction table).
  task_access has: task_id → tasks.id  AND  user_id → profiles.id.
  Each row in task_access represents one link between one user and one task.

The entity-relationship in plain English:
  An ORG has many ROLES, PROFILES, CLIENTS, TASKS, TEMPLATES, ATTENDANCE RECORDS
  A ROLE belongs to one ORG, can have one PARENT ROLE (self-reference)
  A PROFILE belongs to one ORG, has one ROLE
  A CLIENT belongs to one ORG
  A TASK belongs to one ORG, one CLIENT (nullable), one ASSIGNEE (nullable), one CREATOR
  A TASK has many TASK_ACCESS rows, many MESSAGES, many AUDIT_LOG entries
  A USER has many TASK_ACCESS rows (the tasks they can see)

TOPIC 5: INDEXES — WHY QUERIES ARE FAST
================================================================================

What an index is:
The book index analogy: Imagine a 1000-page book about tax law. To find every
mention of "GSTR-3B", you could read all 1000 pages (slow), or look up
"GSTR-3B" in the book's index which tells you: pages 45, 122, 387, 891 (fast).

A database index works the same way. Without an index, PostgreSQL reads EVERY
row to find matches. With an index, it jumps directly to the relevant rows.

Filio's indexes:

  tasks table:
    tasks_org_id_idx — on (org_id)
      Almost every task query filters by org_id. Without this index,
      PostgreSQL reads ALL tasks in the table to find the ones for a specific org.
      With it, it jumps directly to that org's tasks.

    tasks_assignee_id_idx — on (assignee_id)
      "My tasks" queries filter by assignee_id = current user.

    tasks_status_idx — on (status)
      Filter overdue tasks (status != 'completed'), count by status, etc.

    tasks_due_at_idx — on (due_at)
      "Overdue tasks" queries: due_at < now. Without this, full table scan.

  task_access:
    task_access_task_id_idx — on (task_id) — "who has access to this task?"
    task_access_user_id_idx — on (user_id) — "what tasks can this user see?"

  notifications:
    notifications_user_id_idx — on (user_id) — "this user's notifications"
    notifications_is_read_idx — on (is_read) — "all unread notifications"

  recurring_templates:
    recurring_templates_org_active_idx — on (org_id, is_active)
      Composite index: the cron queries active templates per org frequently.

The trade-off of indexes:
  Indexes make SELECT (reads) faster but make INSERT/UPDATE/DELETE (writes) slower
  because the index must also be updated. For a read-heavy app like Filio (task
  lists, dashboards are read far more often than created), more indexes are worth it.

TOPIC 6: DRIZZLE ORM — TYPESAFE QUERIES
================================================================================

What an ORM is:
ORM stands for Object-Relational Mapper. It lets you write database queries in
your programming language (TypeScript) instead of raw SQL. The ORM translates
your TypeScript into SQL.

Why Drizzle specifically (not Prisma, not Sequelize)?
  1. No binary engine. Prisma ships a separate binary (query engine) that runs
     SQL. Drizzle compiles to plain SQL strings. For Supabase's PgBouncer pooler,
     this matters (see prepare:false below).
  2. TypeScript-first. Drizzle infers column types directly from the schema
     definition. Every query result is fully typed.
  3. Lightweight. No hidden magic.

The prepare:false setting:
  Supabase uses PgBouncer as a connection pooler in TRANSACTION MODE.
  A "prepared statement" is a pre-compiled query plan stored on the database
  connection. But PgBouncer in transaction mode does not guarantee that the
  same connection handles consecutive requests from the same app instance.
  So a prepared statement created on connection #5 might not exist when
  the next request goes to connection #12.
  Result: "prepared statement already exists" or "prepared statement not found" errors.
  Fix: prepare: false in Drizzle config. Drizzle sends plain parameterised queries
  instead of prepared statements.

DATABASE_URL vs DATABASE_URL_DIRECT:
  DATABASE_URL — port 6543 — PgBouncer pooler
    Used by the app at runtime. Every web request goes through the pooler.
    Max ~100 actual PostgreSQL connections shared among many app workers.

  DATABASE_URL_DIRECT — port 5432 — direct PostgreSQL connection
    Used ONLY by drizzle-kit (the migration CLI) during development.
    drizzle-kit uses prepared statements internally during schema introspection.
    These need a direct, stable connection — hence the separate URL.
    NEVER use port 5432 in the running app — it would exhaust the connection limit.

How schema.ts maps to the database:
  In src/db/schema.ts, every table is defined with Drizzle's pgTable() function:

    export const tasks = pgTable('tasks', {
      id:          uuid('id').primaryKey().defaultRandom(),
      org_id:      uuid('org_id').notNull().references(() => orgs.id),
      title:       text('title').notNull(),
      task_type:   taskTypeEnum('task_type').notNull(),
      status:      taskStatusEnum('status').notNull().default('not_started'),
      ...
    });

  This generates SQL CREATE TABLE statements when you run drizzle-kit push.
  The TypeScript types for tasks rows are INFERRED from this definition:
    type Task = typeof tasks.$inferSelect;  // the type of a row you SELECT
    type NewTask = typeof tasks.$inferInsert; // the type of a row you INSERT

TOPIC 7: ROW LEVEL SECURITY (RLS)
================================================================================

What RLS is:
Normal database permissions say: "This user can SELECT from the tasks table."
Row Level Security adds: "This user can only SELECT rows from the tasks table
WHERE certain conditions are true."

The nightclub bouncer analogy:
Normal permissions: "You are allowed in the VIP section."
RLS: "You are allowed in the VIP section, but you can only sit at the tables
assigned to you." The bouncer at each table checks a list before letting you sit.

RLS is enabled on ALL 11 tables in Filio.

The 4 security helper functions (SECURITY DEFINER):
  These are PostgreSQL functions that can look up data with elevated privileges.
  They are created once and referenced by policies.

  get_my_org_id():
    SELECT org_id FROM profiles WHERE id = auth.uid()
    Returns the org_id of the currently authenticated user.
    Used by: almost every SELECT policy.

  is_org_admin():
    SELECT is_org_admin FROM profiles WHERE id = auth.uid()
    Returns true if the current user is an org admin.
    Used by: policies that require admin access (roles, clients, recurring_templates).

  is_task_member(task_id):
    SELECT EXISTS(SELECT 1 FROM task_access
                  WHERE task_id = p_task_id AND user_id = auth.uid())
    Returns true if the current user has any access row for this task.
    Used by: tasks SELECT, task_messages SELECT, task_audit_log SELECT.

  Why a helper function instead of inline check?
    If the tasks SELECT policy needed to check task_access, and task_access SELECT
    policy checked tasks, infinite recursion would occur. The SECURITY DEFINER
    function breaks this cycle by running with elevated privileges directly.

SECURITY DEFINER explained:
  A normal database function runs with the caller's permissions.
  A SECURITY DEFINER function runs with the CREATOR's permissions (the database
  superuser). This lets the function read the profiles table to get org_id even
  when called inside a policy that is checking profiles access.

The policies in plain English:

  orgs: "You can only see your own org row."

  roles: "You can see all roles in your org. Only admins can create/edit/delete."

  profiles:
    SELECT: "You can see all profiles in your org." (needed for assignee dropdowns)
    UPDATE: "You can only update your own profile row. And you cannot change your
             own admin status, org membership, or active status." (WITH CHECK clause)

  clients: "See all clients in your org. Only admins can create/edit."

  tasks:
    SELECT: "You can see a task if: it is in your org AND (it is open pool OR
             you have a row in task_access for it)."
    INSERT: "You can create a task if its org_id matches your org."
    UPDATE: "You can update a task if it is in your org and you are a task member."

  task_access:
    SELECT: "You can see access rows for tasks you are a member of."
    NO INSERT/UPDATE/DELETE policies — admin client only.

  task_messages:
    SELECT: "You can read messages for tasks you are a member of."
    INSERT: "You can add a message if you are a task member AND sender_id = your user id."
    (sender_id = auth.uid() prevents impersonating someone else)

  task_audit_log:
    SELECT: "You can read audit entries for tasks you are a member of."
    NO INSERT/UPDATE/DELETE — period. Immutable at the RLS layer.

  attendance_records:
    SELECT: "You can see your own records, OR if you are an admin, see all."
    INSERT/UPDATE: "Only admins can mark attendance."

  notifications:
    SELECT: "You can only see your own notifications."
    UPDATE: "You can mark your own notifications as read."
    NO INSERT — admin client only creates notifications.

Why WITH CHECK (true) is ABSOLUTELY PROHIBITED:
  WITH CHECK (true) on an INSERT policy means "anyone can insert any row".
  If someone created a notifications INSERT policy with WITH CHECK (true),
  any authenticated user could insert a notification into ANY user's inbox.
  Or insert a task into ANY org's task list. This is a critical vulnerability.
  Every policy must specify the exact conditions.

TOPIC 8: SOFT DELETES — NEVER DELETE FROM
================================================================================

What hard delete means:
  DELETE FROM tasks WHERE id = 'xyz';
  The row is gone. Forever. Cannot be recovered.

What soft delete means:
  UPDATE tasks SET is_active = false WHERE id = 'xyz';
  The row still exists. is_active = false means "treat this as deleted".
  All queries add AND is_active = true to filter out "deleted" rows.

Why Filio uses soft deletes for everything:
  1. Audit trail: If a task is hard-deleted, its audit log references a row
     that no longer exists. The audit log becomes meaningless.
  2. Historical reports: The partner wants to see all work done for a client
     this year, including tasks that were "cancelled". Soft deletes preserve this.
  3. Recovery: If something is accidentally deleted, it can be recovered by
     setting is_active = true. Hard delete = permanent loss.
  4. Regulatory: CA firms may be required to keep records for 7 years.

What has is_active:
  - tasks
  - profiles (deactivated users, not deleted)
  - clients (retired clients, not deleted)
  - recurring_templates (paused templates)
  - roles

TOPIC 9: THE UPSERT PATTERN
================================================================================

What UPSERT means:
UPDATE + INSERT. If a row already exists, update it. If it doesn't, insert it.
SQL: INSERT ... ON CONFLICT DO UPDATE ...

Where Filio uses it:

  1. attendance_records:
     The table has UNIQUE (user_id, date).
     If you mark attendance for July 18 for Rahul and he was "present",
     then later update it to "half_day", you don't create TWO records for July 18.
     The upsert finds the existing record (same user_id + date) and updates the status.

     db.insert(attendance_records)
       .values({ user_id, date, status })
       .onConflictDoUpdate({
         target: [attendance_records.user_id, attendance_records.date],
         set: { status, note }
       })

  2. task_access (grantTaskAccess):
     If a user already has viewer access and you want to upgrade them to editor,
     upsert on (task_id, user_id) — updates access_level without creating a duplicate.

Why UNIQUE constraints enable upsert:
  The database needs a way to detect "this already exists". The UNIQUE constraint
  on (user_id, date) is what defines "already exists" for attendance.
  Without the unique constraint, the upsert cannot target the conflict.

TOPIC 10: MULTI-TENANCY IN DEPTH
================================================================================

The org_id pattern:
  Every data table has org_id as the second column (after id).
  Every query MUST include WHERE org_id = <current user's org>.
  This is enforced at two levels: application code (Drizzle) and database (RLS).

How org_id is obtained safely:
  The server action calls resolveUser() which:
  1. Gets the authenticated user's ID from the JWT (verified by Supabase)
  2. Queries the profiles table for that user's org_id
  3. Uses THIS org_id for all subsequent queries

  The org_id CANNOT come from the request URL or request body.
  If a user could pass ?org_id=<other_firm_id> and the app trusted it, they could
  see another firm's data. The org_id must always come from the server-side lookup
  of the authenticated user's own profile.

Cross-tenant attack scenario and how it's prevented:
  Attacker is a member of "Fake Firm" org (id: 'attacker-org-id').
  They send a request with org_id = 'sharma-associates-org-id' in the body.
  The server action ignores the body's org_id entirely.
  It looks up the attacker's profile → gets org_id = 'attacker-org-id'.
  All queries use 'attacker-org-id'. Sharma & Associates data: inaccessible.

The database as the last guard:
  Even if a developer writes a bug and forgets the org_id filter in Drizzle,
  the RLS policy still filters at the database level.
  Example: tasks SELECT policy: "org_id = get_my_org_id()"
  A bugged Drizzle query that fetches all tasks without org_id filter will
  STILL only return the current user's org tasks — PostgreSQL silently filters.

TOPIC 11: INTERVIEW QUESTIONS ABOUT THE DATABASE
================================================================================

Q: Why 11 tables? Couldn't you combine some?

A: Each table has a single, clear responsibility. task_access is separate from tasks
   because access control is a distinct concern — many users can have access to one task.
   task_audit_log is separate because it has different immutability requirements.
   Combining would mean relaxing constraints. The 11-table design follows the Single
   Responsibility Principle applied to database tables.

Q: What is N+1 query problem? Does Filio have it?

A: N+1 means: 1 query to get N records, then N MORE queries to fetch related data.
   Example: 1 query to get 50 tasks, then 50 queries to get each task's client name.
   Total: 51 queries. This is catastrophic at scale.
   Filio uses Drizzle's 'with' relation loading to fetch tasks WITH their clients
   in a SINGLE query using a JOIN. The dashboard stats use Promise.all() to run 5
   count queries in parallel. The digest cron uses 2 batch queries instead of
   4 × N sequential queries.

Q: How do you handle the fact that Drizzle and Supabase admin client are two
   different ways to access the database? Can you use transactions across both?

A: No. Drizzle connects via postgres-js (DATABASE_URL pooler). Supabase admin client
   connects via the Supabase REST API (PostgREST). These are two completely separate
   connection paths. Atomic transactions across them are impossible.
   The compensating action pattern handles failures: if the second operation fails,
   manually undo the first operation (delete the task if task_access fails).
   This is eventually consistent, not ACID-atomic. For a CA task management app,
   this is acceptable — a brief window where a task exists without access rows is
   fine if it is resolved within milliseconds by the rollback.

Q: Why is profiles.id not a foreign key to auth.users.id in Drizzle?

A: auth.users is managed by Supabase in a separate PostgreSQL schema ('auth').
   Drizzle's schema is in the 'public' schema. Cross-schema foreign keys would
   require Drizzle to import the auth schema, which it doesn't manage. The link
   is enforced by convention (the application always creates the auth user first,
   then creates the profile with the matching UUID) and by operational practice
   (inviteUser creates both in the same server action). If a profile UUID doesn't
   match an auth user, the auth check would fail before ever reaching the profile lookup.

Q: What is a recursive CTE and where does Filio use it?

A: CTE = Common Table Expression. A named subquery you can reference in the main query.
   Recursive CTEs reference themselves, allowing them to traverse tree structures.
   Filio's org hierarchy (roles with parent_role_id) forms a tree. To find "all roles
   beneath Manager", you need to traverse the tree recursively.
   getUserSubtree() in src/lib/utils/hierarchy.ts uses a recursive CTE:
     WITH RECURSIVE subtree AS (
       SELECT id FROM roles WHERE id = <start_role_id>
       UNION ALL
       SELECT r.id FROM roles r INNER JOIN subtree s ON r.parent_role_id = s.id
     )
   This starts at a given role and follows parent_role_id links downward until no more
   children. Used to determine who a user can assign tasks to (only people below them
   in the hierarchy).

Q: What happens to performance as the database grows to 10,000 tasks?

A: The indexes on org_id, assignee_id, status, and due_at ensure queries stay O(log n)
   even with 10,000+ tasks. The org_id index means the query only scans rows for one
   firm, not all firms. The due_at index makes overdue queries (due_at < now) instant.
   The task_access indexes ensure "tasks I can see" lookups stay fast. The real
   performance concern at scale would be the digest cron — but its batched query approach
   (load all task_access in 1 query, all tasks in 1 query, build maps in memory) keeps
   it O(n) in memory rather than O(n) in database round trips.
