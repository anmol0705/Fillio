ABOUT THE PROJECT — READ THIS CAREFULLY
================================================================================

The project is called FILIO. It is a work management application built for CA
(Chartered Accountant) firms in India. CA firms are accounting practices that
help businesses with tax filing, audits, GST returns, company registrations, etc.

THE PROBLEM FILIO SOLVES:
Most CA firms run on WhatsApp. The partner (boss) sends work via WhatsApp
messages. Nobody tracks who was assigned what. Deadlines get missed. Nobody
knows the status of a client's tax filing. When the client calls asking about
their GST return, the partner has to scroll through 3 WhatsApp groups to find
out. This causes missed deadlines, penalties, embarrassment, and lost clients.

WHAT FILIO DOES:
- Every piece of work (a task) is created with: a title, a category (GST/TDS/etc.),
  a status (not started → in progress → under review → approved → filed → completed),
  a priority, a due date, an assignee (who is doing it), and a client (whose work it is).
- Every status change, comment, and file is logged permanently (audit trail).
- The partner opens one screen and sees every overdue task in red, who owns it,
  and what is coming due this week.
- Recurring tasks (monthly GST filing, quarterly TDS returns) are generated
  automatically — nobody has to remember to create them.
- The team chats inside the task itself — no WhatsApp needed.

WHO USES IT:
- The founding partner (the boss) — needs the accountability view.
- Managers — assign and review work.
- Article assistants (trainees) — do the work, update statuses.
- One CA firm is one "organisation" (called an org). Multiple CA firms can use
  the same Filio app — they never see each other's data.

TECHNOLOGY STACK (WITH SIMPLE EXPLANATIONS)
================================================================================

Frontend (what the user sees):
  Next.js 15 — A framework built on top of React. Think of React as Lego bricks.
               Next.js gives you a box with pre-built Lego arrangements for common
               patterns (pages, routing, server code, etc.).
  TypeScript — JavaScript with type labels. If a function expects a number and you
               accidentally pass a string, TypeScript tells you before the code runs.
  Tailwind CSS v4 — A utility CSS library. Instead of writing separate CSS files,
                    you put class names directly on HTML elements.
  shadcn/ui — Pre-built UI components (buttons, modals, tables) that you own —
              the code lives in your project, you can modify it.

Backend (what handles the logic):
  Next.js Server Actions — Functions that run on the server, called directly from
                           the browser. No separate backend API needed. Think of it
                           as the checkout counter at a store — you hand over your
                           order (form submission) and the counter does all the work.
  Zod — A validation library. Before saving anything to the database, Zod checks
        that the data has the right shape. Like a form that rejects invalid input.

Database:
  PostgreSQL — A relational database. Data lives in tables with rows and columns,
               like a very powerful spreadsheet. Tables can be linked to each other.
  Supabase — A hosted service that runs PostgreSQL for you, plus gives you
             authentication, file storage, real-time updates, and a dashboard.
             Think of Supabase as a cloud-hosted database with bonus features.
  Drizzle ORM — A TypeScript library that lets you write database queries in
                TypeScript instead of raw SQL. It converts TypeScript code to SQL.

Real-time (live updates without refreshing):
  Supabase Realtime — Uses WebSockets to push database changes to the browser
                      instantly. When a team member posts a message in a task,
                      everyone else on that task sees it immediately.

Email:
  Resend — An email delivery service with a TypeScript SDK. Filio uses it to
           send daily digest emails to each team member summarising their
           overdue tasks.

Hosting:
  Vercel — Deploys the Next.js app. Every time you push code to GitHub, Vercel
           automatically deploys the new version. Also runs cron jobs (scheduled
           tasks) for Filio.

THE 5 MOST IMPORTANT SYSTEM DESIGN CONCEPTS IN FILIO
================================================================================

--- CONCEPT 1: MULTI-TENANCY ---

What it means:
Multiple CA firms (organisations) use the SAME application and SAME database,
but they NEVER see each other's data. This is called multi-tenancy.

The real-world analogy:
Think of a hotel. Many guests stay in the same building. They share the lobby,
the elevator, the pool. But each guest has their own room with a locked door —
they cannot enter another guest's room. The hotel is multi-tenant.

How Filio does it:
Every table in the database has an org_id column. Every piece of data (task,
client, user) is tagged with which organisation it belongs to. Every query
always filters by org_id so Sharma & Associates never sees Patel Tax Consultants'
client data.

Two layers of protection:
  Layer 1 — Application code: Every Drizzle query includes eq(table.org_id, orgId).
  Layer 2 — Database RLS (Row Level Security): PostgreSQL itself refuses to return
             rows to a user if they don't belong to that user's org.

Why two layers?
If a developer makes a mistake and forgets the org_id filter in the code, the
database is still the last guard. Belt AND suspenders.

--- CONCEPT 2: THE TASK ACCESS MODEL ---

What it means:
Not every user can see every task. A task is visible to a user ONLY if they
have a row in the task_access table for that task.

Why this matters:
In a CA firm, some work is confidential. A partner might create a task for a
high-profile client and only want the assigned manager to see it — not all
article assistants.

How it works:
When a task is created:
  - The creator gets an "owner" access row
  - The assignee (if different from creator) gets an "editor" access row
  - Nobody else can see the task

Access levels:
  owner  — can change any field, reassign, delete (soft), grant access to others
  editor — can update the status, send chat messages
  viewer — can read and send messages

The open pool exception:
Tasks with is_open_pool = true are visible to ALL org members. This is for
unassigned work that anyone can pick up and claim.

--- CONCEPT 3: THE AUDIT LOG (IMMUTABILITY) ---

What it means:
Every action on a task (created, status changed, reassigned, comment added)
is recorded permanently in the task_audit_log table. These records CANNOT be
modified or deleted by anyone — not even by the application code.

Why this matters:
If a client says "you never filed my GST return on time", the firm can open
the audit log and show exactly who did what and when. This is legal evidence.
If audit log rows could be edited or deleted, it would be worthless.

How immutability is enforced:
  - The database has NO UPDATE or DELETE policy on task_audit_log.
  - PostgreSQL will reject any UPDATE or DELETE attempt.
  - Even the service role (which bypasses RLS) is never used to update audit rows
    in the application code.
  - Inserts go through the service role (admin client) only — not through user
    sessions — so a user cannot forge an audit entry.

--- CONCEPT 4: THE RECURRING ENGINE ---

What it means:
CA firms have predictable, repetitive work. GSTR-3B must be filed every month
by the 20th. TDS returns every quarter. Instead of the partner manually creating
these tasks every month, Filio generates them automatically from templates.

How it works:
  1. An admin creates a "recurring template": "File GSTR-3B, monthly, assign to
     Manager role, priority: urgent, due 7 days from creation".
  2. Every night at 1 AM, a cron job runs.
  3. For each active template, it checks: "Is today the 1st of the month?" (all
     recurring tasks fire on the 1st). If monthly: always yes. If quarterly: only
     Jan/Apr/Jul/Oct. If annually: only April (start of Indian financial year).
  4. If yes, it creates a new task automatically with the right assignee, due date,
     client, and priority.

Indian FY half-year logic (a subtle bug that was fixed):
  The Indian financial year runs April to March. "Half-yearly" means:
  - April to September → task due September 30
  - October to March → task due March 31
  An earlier version had a bug where January/February/March (months 0/1/2 in code)
  were incorrectly returning September 30 instead of March 31. Fixed.

--- CONCEPT 5: THE REALTIME ARCHITECTURE ---

What it means:
When you are on a task's detail page, the chat updates instantly when someone
else sends a message. No page refresh needed.

The old way (polling):
Every 5 seconds, the browser asks the server "any new messages?" This wastes
bandwidth and has a 5-second delay.

The Supabase Realtime way:
The database is configured to broadcast changes over a WebSocket. The browser
subscribes to that channel. When a new task_messages row is inserted, the
database instantly pushes it to all subscribers. Zero polling, near-instant.

Notification bell:
Works the same way — the browser holds an open WebSocket subscription to the
notifications table filtered to the current user's ID. When a notification is
inserted (task assigned, status changed to review), it instantly appears as an
unread badge on the bell icon.

Why NOT SSE (Server-Sent Events) for notifications?
An earlier design tried to use SSE — a long-lived HTTP connection from the server.
The problem: Vercel serverless functions can be killed at any time (they are
stateless). The SSE connection would be cut. Supabase Realtime is designed to
run in the browser with automatic reconnection built in. The browser is the right
place to hold the WebSocket — not the server function.

================================================================================
ARCHITECTURE DECISIONS (INTERVIEW QUESTIONS)
================================================================================

Q: Why Next.js instead of separate frontend + backend?

A: Next.js Server Actions let you write functions that run on the server and call
   them directly from React components, with full TypeScript types end-to-end.
   For a small team building fast, this eliminates:
   - Separate Express/Fastify API server
   - API route definitions
   - HTTP client (fetch/axios) boilerplate
   - Type mismatches between frontend and backend
   The trade-off: harder to scale backend independently if needed later. For a
   CA firm SaaS with a small team, this is the right trade-off.

Q: Why Supabase instead of rolling your own auth and database?

A: Supabase bundles PostgreSQL + Auth + Realtime + Storage + Row Level Security
   in one managed service. Building Auth alone (JWT, refresh tokens, password reset,
   magic links, session management) would take weeks. Supabase gives all of this
   on day one. The trade-off: vendor dependency. But for a product aimed at a
   specific CA firm, shipping fast matters more than avoiding vendor lock-in.

Q: Why Vercel instead of a VPS or the firm's own server?

A: Vercel is zero-ops. Push to GitHub, it deploys. Automatic SSL, global CDN,
   cron jobs, environment variable management. Running Next.js on the firm's own
   server would require: Linux setup, Nginx, SSL certificates (certbot), PM2,
   monitoring, backups, updates. The firm is not a tech company — they should not
   run servers. The trade-off: ongoing cost (Vercel Pro is ~$20/month) vs. the
   operational cost of a self-hosted setup.

Q: Why PostgreSQL instead of MongoDB?

A: CA firm work is highly relational. A task belongs to a client, is assigned to
   a user, has an audit log, has chat messages, is part of an org. These relations
   are the core of the data model. PostgreSQL handles relations natively with
   foreign keys, joins, and recursive CTEs (for the org hierarchy). MongoDB stores
   documents and does not natively enforce relationships. Row Level Security
   (the security layer) is also a PostgreSQL-specific feature — it does not exist
   in MongoDB.

Q: How does the app handle concurrent users from multiple CA firms?

A: Supabase manages connection pooling via PgBouncer (a connection pooler that
   sits in front of PostgreSQL). Instead of each web request opening a new
   database connection (PostgreSQL has a hard limit, e.g. 100 concurrent connections),
   PgBouncer maintains a pool of N connections and distributes requests through them.
   The app connects to port 6543 (pooler), not port 5432 (direct). Drizzle ORM is
   configured with prepare: false because PgBouncer in transaction mode does not
   support prepared statements (a prepared statement is a cached query plan —
   PgBouncer does not preserve these across connection hops).

Q: What is the security model? How do you prevent one org from seeing another's data?

A: Two independent layers:
   Layer 1 (application): Every Drizzle query includes eq(table.org_id, orgId)
   where orgId comes from the authenticated user's own profile — not from the
   request URL or body.
   Layer 2 (database): PostgreSQL Row Level Security policies are enabled on all
   11 tables. Even if a developer forgets the org_id filter in code, the database
   will silently filter rows. The key function is get_my_org_id() which runs inside
   the database and returns the current user's org_id.

Q: What happens if the recurring task cron job fails halfway through?

A: The cron processes each template independently. If template #3 fails, templates
   #4, #5 continue. There is no global transaction. A specific safety mechanism:
   if a task row is created but the subsequent task_access insert fails (these are
   two separate database clients — no distributed transaction is possible), the task
   row is immediately deleted so no "orphan" task exists (visible to nobody because
   it has no access rows, but wasting space). Missed crons are detected via
   Healthchecks.io — a dead-man's-switch service that alerts if the ping does not
   arrive within the expected window.

Q: How do you scale this if 100 CA firms sign up?

A: The architecture is already multi-tenant. Adding more orgs requires no code
   changes. The scalability levers:
   - Database: Supabase scales vertically (larger instance) or read replicas
   - Serverless functions (Vercel): scale automatically per request
   - Connection pooler (PgBouncer): already handles concurrent connections
   - Cron jobs: if digest cron takes too long for 100 firms, add batching per org
   The current digest cron already handles this: it does 3 batch queries instead of
   N queries per user. At 100 firms with 20 users each = 2000 users, the batch
   approach stays fast.
