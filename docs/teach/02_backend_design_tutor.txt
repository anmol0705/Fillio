ABOUT THE PROJECT
================================================================================

Filio is a work management application for CA (Chartered Accountant) firms in
India. CA firms manage tax filings, audits, GST returns, and company registrations
for their clients. The app replaces WhatsApp-based task coordination with a
structured, auditable system.

The backend is built entirely in Next.js using:
- Server Actions for all mutations (creating, updating, deleting)
- Server Components for reading data
- Route Handlers for API endpoints (cron jobs, health check)
- Supabase for the database, authentication, and real-time
- Drizzle ORM for type-safe database queries
- Zod for input validation

There is NO separate backend server. Next.js runs everything.

TOPIC 1: WHAT IS A SERVER ACTION?
================================================================================

The simple explanation:
In a normal web app, you have two separate programs:
  1. The FRONTEND (React, runs in the browser)
  2. The BACKEND (Express/Django, runs on a server)

When the frontend wants to save data, it sends an HTTP request to the backend.
The backend processes it and returns a response.

Server Actions collapse this into ONE step. You write a function in your
Next.js app, mark it with 'use server', and you can call it directly from a
React component. Next.js handles the HTTP request behind the scenes.

The post office analogy:
Old way: You (frontend) write a letter, put it in an envelope, drive to the
post office, give it to a clerk who drives to the recipient (backend).

Server Actions: You hand the letter directly to a person standing next to you
who has a direct phone line to the recipient. No envelope, no driving.

What a Server Action looks like in Filio (simplified):
  // In src/actions/tasks.ts
  'use server';

  export async function createTask(input) {
    // This runs on the server, not in the browser
    const user = await getCurrentUser();     // who is calling this?
    const task = await db.insert(tasks)...  // save to database
    return { data: task };
  }

  // In a React component (browser code):
  import { createTask } from '@/actions/tasks';

  const result = await createTask({ title: 'File GSTR-3B', ... });

Why use Server Actions instead of a REST API?
  - No separate API server to maintain
  - TypeScript types are shared — no mismatch between what you send and expect
  - Less boilerplate (no route definitions, no fetch calls, no error parsing)
  - For a small team building fast, this is the pragmatic choice

The trade-off:
  - Harder to expose the same actions to a mobile app (you would need REST)
  - Tighter coupling between frontend and backend

TOPIC 2: HOW AUTHENTICATION WORKS
================================================================================

The full sign-in flow, step by step:

STEP 1 — User goes to /login, enters email and password.

STEP 2 — signInAndVerifyProfile() is called.
  This is a client function in src/lib/auth/signIn.ts.
  It calls supabase.auth.signInWithPassword({ email, password }).
  If the password is wrong, Supabase returns an error. Done.

STEP 3 — If password is correct, Filio does an extra check.
  Does a profile row exist for this user in the profiles table?
  Why? It is possible to create a user in Supabase Auth without creating a
  profile row. If that happens, the user would be authenticated but every
  server action would fail (no profile = no org_id = cannot do anything).
  If no profile: sign them out, redirect to /login?error=no_profile.

STEP 4 — Supabase sets HTTP-only cookies.
  These cookies contain:
  - Access token (JWT, short-lived, ~1 hour)
  - Refresh token (long-lived, used to get a new access token)
  The cookies are HTTP-only — JavaScript in the browser CANNOT read them.
  This prevents XSS attacks (malicious scripts stealing the token).

STEP 5 — Every request goes through the middleware.
  The middleware is in src/proxy.ts (called by src/middleware.ts).
  It runs BEFORE every page loads.
  It calls supabase.auth.getUser() to verify the user is still logged in.
  If not logged in and the page is protected: redirect to /login.
  If logged in and on the login page: redirect to /dashboard.

IMPORTANT: Why getUser() and NOT getSession()?
  getSession() reads the JWT from the cookie and trusts it blindly.
  If an attacker steals or forges a cookie, getSession() would accept it.
  getUser() sends the JWT to Supabase's auth server to verify it every time.
  This is slower (one extra network call per request) but much safer.
  CLAUDE.md rule #5: "NEVER use getSession() in middleware."

STEP 6 — getCurrentUser() in Server Components
  In src/lib/auth/getUser.ts, getCurrentUser() is wrapped with React's cache().
  cache() means: if 5 Server Components on the same page all call
  getCurrentUser(), only ONE network call to Supabase is made. The result
  is shared across all 5 components in the same request.
  This is called request deduplication.

STEP 7 — resolveUser() in Server Actions
  Every server action that needs auth calls resolveUser():
    a. Call getCurrentUser() (already cached — no extra network call)
    b. Look up the user's profile to get their org_id
    c. Return { userId, orgId } or { error: 'Unauthorized' }

  Every action starts with:
    const ctx = await resolveUser();
    if (isErrorResult(ctx)) return ctx;  // early return if not authenticated

The cookie hotel analogy:
Think of a hotel. When you check in, you get a key card (access token cookie).
The key card has your room number and an expiry date. Every time you use the
elevator (every request), the elevator reads your key card (getUser() validates
the JWT). When the card expires, you go to the front desk for a new one
(refresh token gets a new access token). If someone steals your key card and
fakes a room number (forged JWT), getSession() would let them in — getUser()
calls the front desk to verify the card is real.

TOPIC 3: VALIDATION WITH ZOD
================================================================================

What validation is:
Before saving anything to the database, you check that the data makes sense.
Example: "due_at" should be a valid date string. "priority" should be one of
urgent/high/medium/low. An empty task title should not be allowed.

Why validate on the server?
You could validate in the browser (frontend form validation), but a user can
bypass that by sending a direct HTTP request to your server action. Always
validate on the server where the code cannot be bypassed.

What Zod does:
Zod lets you define a SCHEMA (a description of what valid data looks like).
Then you call schema.safeParse(input) which either returns:
  { success: true, data: validatedAndTypedData }
  OR
  { success: false, error: ZodError with details of what was wrong }

Example from Filio:
  const createTaskSchema = z.object({
    title: z.string().min(1, 'Title is required').max(500),
    task_type: z.enum(['gst', 'tds', 'income_tax', ...]),
    priority: z.enum(['urgent', 'high', 'medium', 'low']),
    due_at: z.string().datetime().optional(),
    assignee_id: z.string().uuid().optional(),
  });

  const parsed = createTaskSchema.safeParse(input);
  if (!parsed.success) return { error: parsed.error.message };
  // parsed.data is now fully typed and guaranteed valid

The bouncer analogy:
Zod is the bouncer at a nightclub. Every person (piece of data) that wants
to enter has to pass the bouncer's check. Wrong format, missing field, invalid
enum value — the bouncer turns them away. Only valid data gets inside
(into the database).

Why safeParse() not parse():
  parse() throws an exception if validation fails — you have to use try/catch.
  safeParse() returns an object with a success flag — cleaner and predictable.
  Server actions return errors as data (not exceptions), so safeParse() fits.

UUID validation:
Every action that takes an ID (task_id, user_id) runs:
  z.string().uuid().safeParse(id)
This prevents SQL injection via malformed IDs like "'; DROP TABLE tasks; --".
If the ID is not a valid UUID, the action returns an error before touching
the database.

TOPIC 4: THE ADMIN CLIENT vs THE REGULAR CLIENT
================================================================================

Two types of Supabase clients exist in Filio:

Regular client (createClient()):
  Uses the publishable key (safe to expose to browser).
  Respects ALL Row Level Security policies.
  A user can only see/write data they are permitted to.

Admin client (createAdminClient()):
  Uses the service role key (SECRET — must NEVER reach the browser).
  BYPASSES all Row Level Security policies.
  Can read and write ANY row in ANY table.

Why does the admin client exist?
Some operations require writing data that the current user is not "allowed"
to write under normal RLS:

  1. task_access inserts: There is no RLS INSERT policy on task_access.
     If there were, a user could grant themselves access to any task.
     So all task_access inserts go through the admin client.

  2. task_audit_log inserts: The audit log must be unforgeable. If users
     could insert their own audit rows, they could fake a history.
     Only the admin client (controlled server code) inserts audit rows.

  3. notifications inserts: When Task A is assigned to User B, a notification
     for User B is created. User A is the one making the request — they do not
     have permission to write into User B's notifications via RLS. Admin client
     bypasses this.

  4. Profile creation: Only org admins can invite new users. The admin client
     creates the auth user AND the profile row (bypassing RLS intentionally).

The nuclear codes analogy:
The admin client is like nuclear launch codes. Incredibly powerful, used for
specific authorised purposes only. If it leaks to the wrong place (a client
component, a public URL), the entire database is exposed. It is stored in
SUPABASE_SECRET_KEY (no NEXT_PUBLIC_ prefix — never sent to browser) and only
imported in src/lib/supabase/server.ts which has 'import server-only' at the top.

'import server-only' is a tiny package that causes a BUILD ERROR if you
accidentally import a server file in a client component. Catches mistakes
before they reach production.

TOPIC 5: MIDDLEWARE AND ROUTE PROTECTION
================================================================================

What middleware is:
Code that runs BEFORE every request reaches its destination.
Like a security guard at a building entrance. Every person (request) must
pass through before going to their floor (page/route).

In Filio, the middleware:
  1. Reads the session cookie
  2. Calls supabase.auth.getUser() to verify authentication
  3. If the user is NOT logged in AND is trying to access a protected page:
     → Redirect to /login
  4. If the user IS logged in AND is on the login page:
     → Redirect to /dashboard (no need to see login again)
  5. If the user IS logged in AND is on a protected page:
     → Also refreshes the session (rotates tokens if expiring soon)

Why is the middleware file split into proxy.ts and middleware.ts?
  Next.js specifically looks for a file named middleware.ts to run middleware.
  The actual logic lives in proxy.ts (cleaner to test, cleaner to import).
  middleware.ts is one line:
    export { proxy as middleware, config } from './proxy';
  The config object tells Next.js which paths to apply middleware to — it
  excludes static files (_next/static, images, favicon) so those load fast
  without going through the auth check.

A critical bug that was fixed:
  The original setup only had proxy.ts — there was no middleware.ts file.
  Next.js never ran the middleware because it was not looking for proxy.ts.
  Route protection was completely non-functional. The fix was creating
  middleware.ts with the one-line re-export.

TOPIC 6: THE TASK ENGINE (BUSINESS LOGIC)
================================================================================

The status workflow:
  not_started → in_progress → under_review → approved → filed → completed
                                    ↑                ↓
                               changes_requested ←←←←

Each transition is ENFORCED by a STATUS_TRANSITIONS map:
  const STATUS_TRANSITIONS = {
    not_started:        ['in_progress'],
    in_progress:        ['under_review'],
    under_review:       ['changes_requested', 'approved'],
    changes_requested:  ['in_progress'],
    approved:           ['filed'],
    filed:              ['completed'],
    completed:          [],  // terminal — no transitions
  }

If a user tries to go from "not_started" directly to "approved", the server
action returns: "Invalid transition: not_started → approved".

Why enforce this server-side?
Frontend validation is not enough — a user can call the API directly with any
status value they want. The server action checks every transition.

Completed tasks are immutable:
  if (task.status === 'completed') return { error: 'Completed tasks are immutable' }
  This check runs FIRST, before the transitions map. Once a task is completed,
  nothing can change it — not even the owner.

The orphan rollback problem:
  createTask does TWO operations:
  1. Insert a row into tasks table (via Drizzle/pooler connection)
  2. Insert row(s) into task_access table (via admin client/Supabase)

  These two operations use DIFFERENT database clients. There is NO transaction
  spanning both. If the task is created but the task_access insert fails, the
  task exists but is invisible to everyone (no access rows → nobody can see it).
  This orphan wastes space and causes confusion.

  The fix: if task_access insert fails, immediately delete the task row:
    const { error: accessError } = await admin.from('task_access').insert(accessRows);
    if (accessError) {
      await db.delete(tasks).where(eq(tasks.id, task.id));
      return { error: 'Failed to create task — access grant failed.' };
    }
  This is called a compensating transaction or compensating action.

The notification flow:
  When a task is assigned to someone different from the creator:
  1. The admin client inserts a notification row for the assignee
  2. The assignee's NotificationBell (in the browser) has a Supabase Realtime
     WebSocket subscription watching their notifications
  3. The new row is pushed instantly to their browser → bell shows unread count

TOPIC 7: THE RECURRING TASK ENGINE
================================================================================

What it solves:
CA firms have predictable recurring work: file GSTR-3B every month, file
TDS return every quarter, file income tax returns every year. Instead of the
partner manually creating these tasks every period, templates auto-generate them.

The flow:
  1. Admin creates a template: "GSTR-3B filing, monthly, assign to Senior Manager
     role, 7 days before due date, priority: urgent"
  2. Every day at 1 AM UTC, a cron job calls /api/cron/recurring
  3. The cron checks: "Is today the 1st of the month?"
     (All recurring tasks fire on the 1st)
  4. For a monthly template: yes, every 1st. For quarterly: Jan/Apr/Jul/Oct.
     For half-yearly: Apr/Oct. For annually: Apr only.
  5. If it's a fire day, create a task from the template.

The role-based assignee resolution:
  Templates store default_assignee_role_id, not a specific user_id.
  Why? Staff change. If you hardcoded "assign to Rahul", and Rahul leaves the
  firm, every future template generation would fail or assign to a deactivated
  user. Role-based assignment survives staff turnover.
  At cron time: find the first active user with that role_id → assign to them.
  If no user found with that role → create as open pool task (anyone can claim).

The half-yearly Indian FY bug (important to understand):
  In JavaScript, months are 0-indexed: January = 0, February = 1, ... December = 11.
  The Indian financial year runs April (month 3) to March (month 2 of next year).
  Half-yearly means:
    April(3) to September(8) → first half → due September 30 (month 9, day 0)
    October(9) to March(2)   → second half → due March 31 (month 3 next year, day 0)

  The original bug used "m <= 8" to check for second half. But 0 (Jan), 1 (Feb),
  2 (Mar) are all <= 8, so January/February/March incorrectly returned September 30
  instead of March 31. Fixed with explicit checks:
    if (m >= 3 && m <= 8) → Sep 30
    if (m <= 2) → Mar 31 this year (Jan/Feb/Mar = second half of CURRENT FY)
    else → Mar 31 next year (Oct/Nov/Dec = second half of NEXT FY starting)

TOPIC 8: THE CRON JOBS
================================================================================

What a cron job is:
A task that runs automatically on a schedule, like a timer. Named after the
Unix "cron" scheduler. The word cron comes from "chronos" (Greek for time).

Filio has 3 cron jobs:

  1. /api/cron/recurring — fires daily at 1 AM UTC
     Generates recurring tasks from templates. See Topic 7.

  2. /api/cron/digest — fires Mon-Sat at 7 AM UTC
     Sends each user a personalised email listing their overdue tasks and
     tasks due in the next 7 days. CA firms work Mon-Sat; Sunday email useless.

  3. /api/cron/compliance — fires daily at 8 AM UTC
     Sends notifications to all org admins about upcoming statutory deadlines
     in the next 7 days (GSTR-3B due soon, TDS return due soon, etc.).

How Vercel runs them:
  vercel.json defines the schedule in cron syntax:
    "0 1 * * *" = "at minute 0 of hour 1, every day" = 1:00 AM daily
  Vercel sends a GET request to the endpoint with an Authorization header.

Security — CRON_SECRET:
  If anyone knew the cron URL, they could trigger mass task generation or
  mass emails at will. All three cron endpoints check:
    Authorization: Bearer <CRON_SECRET>
  Vercel includes this header automatically. Any other caller gets 401.

Why GET, not POST?
  Vercel's cron scheduler sends GET requests. The original handlers exported
  POST — Vercel got 405 (Method Not Allowed) on every fire. All handlers
  were corrected to export GET.

maxDuration = 300:
  By default, Vercel serverless functions time out after 10 seconds.
  Digest email sending 50+ users, or recurring task generation for 10+ firms
  can easily exceed 10 seconds. maxDuration = 300 sets the limit to 5 minutes
  (Vercel Pro allows up to 5 minutes for route handlers).

The digest cron optimisation (O(n) → batched):
  Original approach (broken at scale):
    For each user:
      Query 1: get their task_access rows
      Query 2: get their overdue tasks
      Query 3: get their due-soon tasks
      Query 4: send email
    Total: 4 × N database queries for N users. At 50 users = 200 queries.
    This would time out and each query adds network latency.

  Optimised approach:
    Query 1: get ALL task_access rows for ALL active users (one query)
    Query 2: get ALL overdue/due-soon tasks matching those IDs (one query)
    Build per-user task lists in memory (O(n) in-memory operation, instant)
    Send emails in parallel batches of 10
    Total: 2 database queries + parallel sends. Does not scale with user count.

TOPIC 9: SECURITY PATTERNS
================================================================================

1. import 'server-only'
   Files that must NEVER be loaded in the browser include:
   - src/lib/supabase/server.ts (has the service role key)
   - src/db/index.ts (database connection string)
   - src/lib/auth/getUser.ts (server auth helper)
   Importing 'server-only' makes Next.js throw a BUILD ERROR if these files
   are accidentally imported in a Client Component. Catches the mistake at
   build time, not runtime.

2. Soft deletes (never DELETE FROM)
   No table in Filio ever has a DELETE SQL executed on it.
   To "delete" a task: set is_active = false.
   To "remove" a user: set is_active = false.
   Why? Historical data is the product's value. The audit trail only makes
   sense if the underlying data still exists. A task marked deleted can be
   recovered. A hard-deleted task is gone forever.

3. UUID validation before every query
   Every server action that accepts an ID parameter runs:
     z.string().uuid().safeParse(id)
   If the input is "admin' OR 1=1--" (a SQL injection attempt), this check
   fails immediately and the action returns an error — the input never reaches
   the database.
   With Drizzle ORM and parameterised queries, SQL injection is already
   prevented at the ORM level, but defensive UUID validation adds another layer.

4. Environment variable validation at startup
   src/lib/env.ts loops through all 7 required environment variables.
   If any is missing, the app THROWS on startup.
   This prevents the app from booting with a missing RESEND_API_KEY and then
   silently failing to send emails for weeks without anyone noticing.

5. CSP (Content Security Policy)
   The HTTP headers returned by next.config.ts include a Content-Security-Policy
   header that restricts what scripts can run on the page:
   - Only scripts from the same origin ('self') are allowed
   - 'unsafe-eval' (eval() in JavaScript, used by development tools) is ONLY
     allowed in the development environment. Removed from production.
   This prevents XSS attacks from executing injected scripts.

6. profiles_update_own WITH CHECK
   An earlier RLS policy allowed users to UPDATE their own profile row but had
   no WITH CHECK clause. This meant a user could change their own is_org_admin
   from false to true via a direct PostgREST API call (bypassing the app UI).
   Fixed with:
     WITH CHECK (
       is_org_admin = (SELECT is_org_admin FROM profiles WHERE id = auth.uid())
       -- users cannot change their own admin status
     )

TOPIC 10: ERROR HANDLING PATTERNS
================================================================================

The result-object pattern (no exceptions):
  Every server action in Filio returns either:
    { data: <result> }   — success
    { error: string }    — failure

  Never throws exceptions. The caller always checks:
    const result = await createTask(input);
    if ('error' in result) {
      // show error message to user
      return;
    }
    // use result.data

  Why? Exceptions are hard to type and require try/catch everywhere. The
  result object pattern is explicit — the caller is FORCED to handle both cases
  because TypeScript's discriminated unions make the type checker enforce it.

Per-user error isolation in cron:
  The digest cron sends emails to many users. If one user's email fails
  (Resend API timeout, invalid email address), the loop continues to the next
  user. Errors are collected and returned in the response:
    return { success: true, emailsSent: 47, failed: ['bad@example.com'] }

  If the cron threw on the first error, 47 users would never get their email.
  Fault isolation at the user level is the right design.

Structured JSON logging:
  All three cron routes emit JSON log lines:
    { "level": "info", "cron": "digest", "event": "start", "timestamp": "..." }
    { "level": "info", "cron": "digest", "event": "complete", "emailsSent": 47,
      "duration_ms": 3240 }
  JSON logs are parseable by tools like Datadog, Loki, and Grafana. Plain text
  logs require regex parsing. Structured logs are searchable by field.
