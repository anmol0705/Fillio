ARCHITECTURE — HOW IT ALL FITS TOGETHER
================================================================================

Filio is a UNIFIED full-stack Next.js application. There is no separate backend.

Request flow:
  Browser → Next.js on Vercel (App Router)
    ├── Server Components: render pages server-side, fetch data directly via Drizzle
    ├── Server Actions: all mutations (no REST API — Next.js 15/16 Server Actions)
    ├── Route Handlers: SSE notifications, cron endpoints
    └── Middleware (src/middleware.ts): session refresh + route guard on every request
         └── Calls Supabase auth.getUser() — server-verified, not cookie-read

  Next.js → Supabase (managed PostgreSQL 16)
    ├── Drizzle ORM over transaction pooler (port 6543, prepare: false)
    ├── Supabase Auth: cookie sessions via @supabase/ssr
    ├── Supabase Realtime: CDC WebSocket for task chat + bell notifications
    └── Supabase Storage: private bucket for task file attachments

  Next.js → Resend (email)
    └── Daily digest via cron, task assignment emails

Key architectural decision: WHY NO SEPARATE BACKEND?
- Next.js 16 Server Actions run server-side with full Node.js access
- They can import Drizzle directly — no HTTP hop, no serialization overhead
- For a firm of 5-30 people, the overhead of a REST API adds complexity without benefit
- Server Actions have built-in CSRF protection
- Single deployment unit — simpler CI/CD, no CORS configuration

DATABASE — ALL 11 TABLES
================================================================================

Connection rule (CRITICAL):
- App runtime → DATABASE_URL (port 6543, transaction pooler, prepare: false)
- drizzle-kit push → DATABASE_URL_DIRECT (port 5432, direct, for migrations)
- Wrong port = "prepared statement already exists" error due to pooler state

TABLE 1: orgs
  id uuid PK | name text | slug text unique | created_at timestamptz
  → Root tenant. Every other table has org_id FK.

TABLE 2: roles
  id uuid PK | org_id FK→orgs | name text | color text | parent_role_id FK→roles (self-ref)
  sort_order int | created_at
  → Self-referencing tree for org hierarchy. Recursive CTE traverses it.

TABLE 3: profiles
  id uuid PK (= auth.users.id) | org_id FK→orgs | role_id FK→roles (nullable)
  full_name text | email text | avatar_url (nullable) | is_active bool | is_org_admin bool
  → No FK to auth.users (auth schema is outside Drizzle scope, different PG schema)
  → Soft delete: is_active = false. Never DELETE FROM profiles.

TABLE 4: clients
  id uuid PK | org_id FK→orgs | name text | pan (nullable) | gstin (nullable)
  contact_email (nullable) | contact_phone (nullable) | is_active bool
  → The CA firm's client roster. Every task belongs to a client.

TABLE 5: tasks (CORE ENTITY)
  id uuid PK | org_id FK→orgs | title text | description (nullable)
  task_type enum(gst,tds,income_tax,audit,roc_mca,accounting,payroll,notice,advisory,other)
  status enum(not_started,in_progress,under_review,changes_requested,approved,filed,completed)
  priority enum(urgent,high,medium,low) | client_id FK→clients (nullable)
  assignee_id FK→profiles (nullable) | creator_id FK→profiles
  financial_year text (nullable) | due_at timestamptz (nullable)
  is_open_pool bool | is_active bool | created_at | updated_at
  Indexes: org_id, assignee_id, status, due_at

TABLE 6: task_access (PERMISSION BACKBONE)
  id uuid PK | task_id FK→tasks | user_id FK→profiles
  access_level enum(owner,editor,viewer) | granted_at timestamptz
  Unique: (task_id, user_id)
  → A user sees a task IF AND ONLY IF they have a row in task_access.
  → This is the single source of truth for all task visibility.

TABLE 7: task_messages
  id uuid PK | task_id FK→tasks | sender_id FK→profiles
  content text (nullable) | file_url (nullable) | file_name (nullable) | created_at
  → Supabase Realtime CDC subscription on this table for live chat.

TABLE 8: task_audit_log (IMMUTABLE)
  id uuid PK | task_id FK→tasks | actor_id FK→profiles
  action enum(created,status_changed,reassigned,comment_added,file_uploaded,access_granted)

TABLE 9: recurring_templates
  id uuid PK | org_id FK→orgs | title text | task_type enum | cadence enum(monthly,quarterly,half_yearly,annually)

TABLE 10: attendance_records

  status enum(present,absent,half_day,leave) | note text (nullable) | created_at
  Unique: (user_id, date) → enforces one record per person per day
  → Upsert via onConflictDoUpdate — safe to submit multiple times.

TABLE 11: notifications
  id uuid PK | org_id FK→orgs | user_id FK→profiles | task_id FK→tasks (nullable)

================================================================================
MULTI-TENANCY
================================================================================

Filio serves multiple CA firms from one database. Data isolation is absolute.

Strategy: org_id on every table (except task_access, which is scoped transitively
          through task_id → tasks.org_id)

THREE LAYERS OF ISOLATION:

Layer 1 — Application (Drizzle queries in src/actions/*):
  Every query includes: eq(table.org_id, profile.org_id)
  profile.org_id comes from getCurrentUser() → verified server session → DB lookup.
  Never trust client-provided org_id.

Layer 2 — RLS (Postgres Row Level Security):
  All 11 tables have RLS enabled.
  Four SECURITY DEFINER helper functions (search_path = public, prevents injection):
    get_my_org_id()          → SELECT org_id FROM profiles WHERE id = auth.uid()
    is_org_admin()           → COALESCE((SELECT is_org_admin FROM profiles WHERE id = auth.uid()), false)
    is_task_member(task_id)  → EXISTS (SELECT 1 FROM task_access WHERE task_id=p AND user_id=auth.uid())
    is_task_owner(task_id, user_id) → EXISTS (... AND access_level = 'owner')

  Key RLS policies:
    orgs:              SELECT WHERE id = get_my_org_id()
    profiles:          SELECT WHERE org_id = get_my_org_id()
    tasks:             SELECT WHERE org_id = get_my_org_id() AND (is_open_pool OR is_task_member(id))
    task_access:       SELECT WHERE is_task_member(task_id)
    task_messages:     SELECT WHERE is_task_member(task_id)
    task_audit_log:    SELECT WHERE is_task_member(task_id) — NO INSERT/UPDATE/DELETE
    notifications:     SELECT WHERE user_id = auth.uid() AND org_id = get_my_org_id()
    attendance:        SELECT WHERE org_id = get_my_org_id() AND (user_id = auth.uid() OR is_org_admin())

Layer 3 — Service Role:
  createAdminClient() uses SUPABASE_SECRET_KEY (service role) — bypasses RLS.
  ONLY used for: profile creation, task_audit_log inserts, notifications inserts, task_access grants.
  NEVER in client components, middleware, or route handlers (unless explicitly privileged).

================================================================================
AUTHENTICATION FLOW
================================================================================

1. User visits /login → submits email + password
2. signInAndVerifyProfile():
   - supabase.auth.signInWithPassword()
   - Queries profiles table for matching id
   - If no profile row: signOut() → redirect /login?error=no_profile
   - If profile found: Supabase sets auth cookies → redirect /dashboard

3. src/middleware.ts runs on EVERY request (except static assets):
   - Creates Supabase server client from cookies
   - Calls supabase.auth.getUser() — NEVER getSession()
     WHY: getSession() reads from cookie WITHOUT server verification — spoofable.
          getUser() calls Supabase auth server to verify the JWT.
   - Unauthenticated + protected route → redirect /login
   - Authenticated + auth page → redirect /dashboard
   - Refreshes session cookies on every response (sliding expiry)

4. Server Components call getCurrentUser():
   - Wrapped in React cache() — deduped per request (max 1 DB call per render tree)
   - Returns { id, email } or null

5. POST /auth/logout:
   - supabase.auth.signOut() → clears cookies
   - Never redirected to by the auth page check (excluded from isAuthPage)

CRITICAL RULE: cookies() from next/headers is ASYNC in Next.js 15+.
Always: const cookieStore = await cookies()
Missing the await = runtime error that's hard to debug.

================================================================================
SERVER ACTIONS PATTERN
================================================================================

All mutations use Next.js Server Actions ('use server'). No REST API.

Why Server Actions over REST:
- Run server-side — can import Drizzle directly, no HTTP serialization
- Built-in CSRF protection (same-origin by default)
- TypeScript end-to-end — no need to type request/response bodies separately
- Simpler mental model for a small team
- Co-located with components that use them

Pattern used in every action:
1. getCurrentUser() — verify auth, get user.id
2. DB lookup for profile (org_id, is_org_admin)
3. Zod safeParse() on input
4. UUID validation on any ID from client: z.string().uuid().safeParse(id)
5. Org-scoped Drizzle query
6. Return { data: ... } or { error: string }

ZODV4 NOTE: Zod v4 renamed ZodError.errors → ZodError.issues
Always: parsed.error.issues[0]?.message (not .errors)

REALTIME ARCHITECTURE
================================================================================

TWO realtime channels:

1. TASK CHAT (Supabase Realtime CDC in browser):
   TaskChat.tsx subscribes to INSERT on task_messages filtered by task_id.
   Runs in browser via createBrowserClient().
   Cleanup: useEffect return removes channel.
   File uploads: Supabase Storage → signed URL stored in file_url column.

2. NOTIFICATION BELL (Supabase Realtime CDC in browser):
   NotificationBell.tsx subscribes to INSERT on notifications filtered by user_id.
   Runs in browser via createBrowserClient().

   WHY NOT SSE: Vercel serverless functions have max duration (10s hobby / 300s pro).

   manages its own persistent WebSocket — Vercel doesn't need to keep anything alive.

CRON JOBS (3 jobs, all in vercel.json)
================================================================================

Vercel sends GET requests to the configured path.
All routes export GET (not POST).
All protected by: Authorization: Bearer <CRON_SECRET>

Job 1: /api/cron/recurring — runs at 0 1 * * * (1 AM UTC daily)
  Logic: for each active recurring_template, calculate if today is
  (period_end_date - days_before_due). If yes: create task, grant access, write audit log.
  Period end dates:
    monthly → last day of current month
    quarterly → March 31 / June 30 / Sept 30 / Dec 31
    half_yearly → Sept 30 / March 31
    annually → March 31 (Indian FY end)
  Creates task via admin client. Sets is_open_pool=true if no assignee found.

Job 2: /api/cron/digest — runs at 0 7 * * 1-6 (7 AM UTC, Mon-Sat)
  Logic: for each org admin, fetch overdue + due-today tasks → send React Email via Resend.
  Skips digest if no overdue and no due-today tasks.

Job 3: /api/cron/compliance — runs at 0 8 * * * (8 AM UTC daily)
  Logic: read getUpcomingDeadlines(7) from static deadlines.ts.
  For each deadline: insert notification for each org admin.
  Deduplication: check for existing notification (task_id IS NULL, created today) before inserting.
  Uses admin client for notifications insert (no user-level INSERT policy on notifications).

SECURITY MODEL — SUMMARY
================================================================================

What is NEVER done:
- WITH CHECK (true) in any RLS policy
- getSession() in middleware (use getUser() only)
- SUPABASE_SECRET_KEY exposed to client
- DELETE FROM any table (soft delete only: is_active = false)
- dbDirect connection exported from db/index.ts for app code
- createAdminClient() in client components

What IS done:
- import 'server-only' at top of db/index.ts, server.ts, getUser.ts, deadlines.ts, recurring.ts
  → Build-time error if accidentally imported in a client component
- service_role (admin client) only for: profile creation, audit log, notifications, task_access
- RLS as defence-in-depth (application layer is primary; RLS catches anything that slips through)
- UUID validation on every ID from client: z.string().uuid().safeParse(id).success
- Zod safeParse on all input (not parse — safeParse returns error object, never throws)
- React cache() on getCurrentUser() — prevents multiple auth calls per render
- Security headers in next.config.ts: CSP, X-Frame-Options DENY, HSTS, nosniff

Content Security Policy allows:
  connect-src: self + *.supabase.co (Realtime WebSocket needs wss://*)
  frame-ancestors: none (prevents clickjacking — stricter than X-Frame-Options)

================================================================================
THE TASK ACCESS MODEL (most complex part)
================================================================================

The task_access table is the permission backbone. It answers: "Can this user see this task?"

Access levels:
- owner: created the task, can change assignee, change status, delete (soft)
- editor: assigned to the task, can update status, add messages
- viewer: granted access (e.g. subtree members), can read and comment only

How access is granted:
1. Task creator → owner access inserted via admin client at creation time
2. Assignee → editor access inserted via admin client when task is created or reassigned
3. Org admin → owner access (can always see everything in their org via RLS)
4. Role subtree: when a manager creates a task, getUserSubtree(managerId) returns all
   role IDs below their role via recursive CTE. All profiles with those role IDs get viewer access.

RLS policy for tasks:
  SELECT WHERE org_id = get_my_org_id() AND (is_open_pool = true OR is_task_member(id))

is_task_member() is a SECURITY DEFINER function — avoids recursive RLS policy calls
that would cause infinite loops (policy calling a function that queries a table that also
has RLS that calls the same function).

OPEN POOL: tasks with is_open_pool = true are visible to all org members without
being in task_access. When someone claims a pool task: assignee_id is set,
is_open_pool → false, editor access is inserted, notification sent to original creator.

================================================================================
TASK STATUS WORKFLOW
================================================================================

Valid transitions:
  not_started → in_progress
  in_progress → under_review
  under_review → changes_requested
  under_review → approved
  changes_requested → in_progress  (loop back)
  approved → filed
  filed → completed
  completed → (nothing — immutable)

Enforcement: in updateTaskStatus() server action (application layer).
NOT enforced in RLS — RLS only controls visibility, not business logic.

Every status change: task_audit_log INSERT via admin client with old_value + new_value.

================================================================================
ROLE HIERARCHY (RECURSIVE TREE)
================================================================================

roles table is self-referencing: parent_role_id UUID → roles.id

Example tree:
  Partner (sort_order: 0)
  └── Manager (sort_order: 1)
      ├── Senior Associate (sort_order: 2)
      │   └── Article Assistant (sort_order: 3)
      └── Semi-Senior (sort_order: 2)

getUserSubtree(userId) in src/lib/utils/hierarchy.ts:
  Uses a recursive CTE (WITH RECURSIVE):
  1. Start with the user's role_id
  2. Recursively join roles on parent_role_id
  3. Return all role IDs in the subtree
  Used when creating tasks to grant viewer access to everyone below the creator in the tree.

Drag-and-drop reordering: @dnd-kit/core + @dnd-kit/sortable.
On drop: reorderRoles() server action updates sort_order for all affected roles.
Circular parent validation: updateRole() checks that new parent_role_id is not
a descendant of the role being updated (prevents cycles).

================================================================================
RECURRING ENGINE (DETAILED)
================================================================================

Location: src/lib/cron/recurring.ts (server-only, imported only by cron route)

Algorithm:
1. Load all active recurring_templates from DB
2. For each template:
   a. Call shouldFireToday(cadence, days_before_due, today):
      - Calculate period end date based on cadence
      - fireDate = period_end_date - days_before_due
      - Return true if today === fireDate
   b. If not today → skip
   c. Find org admin profile (creator_id for the generated task)
   d. Find assignee (first active profile with default_assignee_role_id)
   e. Set dueDate = period_end_date at 23:59:59
   f. Insert task via admin client
   g. Insert task_access rows (owner for admin, editor for assignee)
   h. Insert task_audit_log entry
   i. Insert notification for assignee
   j. Increment counter

Period end dates by cadence:
  monthly     → last day of current month (varies: 28/29/30/31)
  quarterly   → March 31, June 30, Sept 30, Dec 31
  half_yearly → Sept 30 (Apr-Sep half) or March 31 (Oct-Mar half)
  annually    → March 31 (Indian financial year end)

PERFORMANCE CONSIDERATIONS
================================================================================

1. React cache() on getCurrentUser() — deduplication within request
2. Promise.all() in layout and pages — parallel DB queries instead of sequential
3. Indexes on tasks: org_id, assignee_id, status, due_at
4. Unique constraint on task_access (task_id, user_id) — fast member lookup
5. Attendance upsert: onConflictDoUpdate instead of SELECT then INSERT/UPDATE
6. SQL ANY(ARRAY[...]) pattern for IN queries on arrays of UUIDs
7. No SELECT * — only select needed columns in most queries
8. prepare: false on Drizzle pooler client — required for transaction pooler (PgBouncer)
   Without prepare:false → "prepared statement X already exists" error in pooler

Known gaps (not yet implemented):
- No server-side pagination on task list (loads all tasks to client, TanStack filters)
- No Redis/Upstash caching layer for dashboard stats
- Recurring cron is sequential per-template (N+1 pattern — should batch)

================================================================================
KNOWN TRADEOFFS TO KNOW COLD (INTERVIEWERS LOVE THESE)
================================================================================

1. Server Actions vs REST API
   CHOSE: Server Actions
   WHY: No HTTP overhead, CSRF protection built in, TypeScript end-to-end
   TRADEOFF: No public API, harder to integrate third-party tools later

2. Drizzle vs Prisma
   CHOSE: Drizzle
   WHY: Better TypeScript inference, works with pooler (prepare:false), no shadow DB
   TRADEOFF: Less mature ecosystem, fewer plugins, more verbose schema definition

3. RLS vs Application-only tenancy
   CHOSE: Both (defence in depth)
   WHY: Application layer is the primary guard (faster). RLS is the safety net.
   TRADEOFF: RLS adds per-query overhead. SECURITY DEFINER functions must be carefully written.

4. Soft delete vs Hard delete
   CHOSE: Soft delete (is_active = false)
   WHY: Historical data is valuable. Audit trail requires past state. Recoverable mistakes.
   TRADEOFF: All queries must filter is_active = true. Soft-deleted rows accumulate.

5. Static compliance calendar vs Dynamic sync
   CHOSE: Static (hardcoded FY 2026-27)
   WHY: Government deadlines rarely change mid-year. Fastest to build. Zero infra cost.
